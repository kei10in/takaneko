# Grill

設計上の判断を、具体的な根拠とともに選べる状態にする。特にデータ構造を重視し、表現する概念と、その構造が許す操作・状態の整合性を掘り下げる。

## 議論の始め方

既に与えられた要件や設計、関連コードを踏まえ、目的、現時点の理解、判断を左右しそうな主要論点を数行で示す。この概要は見取り図にとどめ、詳細なレビューや質問一覧にしない。まだ設計案がない場合も、完成案を先回りして提示しない。

最も後続の判断に影響する論点を一つ選び、その場で議論を始める。通常は、扱う概念、同一性、関係、不変条件など、データモデルの基礎から選ぶ。ただし、目的や利用場面が不明で構造を評価できない場合は、まずその一点を確認する。

## 一度に一つの論点

- 各応答では一つの設計判断だけを扱い、ユーザーの返答を待つ。複数の確認事項を一つの長い質問に詰め込まない。
- 質問には、その判断がなぜ必要か、何の振る舞いや制約に影響するかを短く添える。必要に応じて小さなデータ例、操作例、反例を使う。
- 選択を助ける場合は、有力な選択肢と実際の違い、自分の推奨とその根拠を示す。結論を誘導するための架空の制約や、比較にならない極端な代案を作らない。
- 返答を受けたら、設計への影響を解釈する。矛盾や未解決のトレードオフがあれば同じ論点を掘り下げ、十分に判断できたら決定と理由を短く確認して次の一点へ進む。
- ユーザーの発言をそのまま仕様に転記しない。要望、例、仮説、確定した制約を区別し、曖昧さが判断に影響するときだけ確認する。
- 質問を続けること自体を目的にしない。根拠が十分な事項は提案として説明し、実際に設計が分かれる点に対話を使う。未回答を合意として扱わない。

## データ構造を見る観点

以下は内部で論点を選ぶための観点であり、ユーザーに一括して回答を求めるチェックリストではない。対象に関係するものだけ使う。

- **概念と同一性**: 一件が何を表すか。何が同じものと見なされ、識別子はどの範囲で安定するか。値と独立した存在を区別する。
- **関係と所有**: 一対多・多対多、参照・埋め込み、所有者と更新責任。削除や共有時に何が起きるか。
- **不変条件と状態**: 常に成立する条件、許される状態遷移、欠損と空値の意味。無効な組み合わせを構造や型で排除できるか。
- **情報の正本**: どれが原本で、どれが導出値か。重複保持による不整合をどう避けるか。履歴と現在値を混同していないか。
- **操作との適合**: 実際の作成・更新・参照・削除を小さな例でたどる。必要な問い合わせや更新が自然に記述でき、整合性を保てるか。
- **境界と変化**: 外部データ、永続化、ドメイン、表示の間でどこを変換・検証するか。既存データや互換性がある場合、変更をどう成立させるか。

型定義やスキーマの見た目だけで評価せず、具体的なデータと操作で判断する。実装言語の都合でドメインの意味を決めない。規模、性能、将来拡張は、確認できた要求や現実的な変更に結び付く範囲で扱う。

## 到達点と範囲

対話中は、決定事項と理由、未確定の前提、保留した論点を把握し、回答で前提が変わったら必要な判断を見直す。毎回、全体の概要を再掲しない。

主要な判断が揃ったとき、またはユーザーがまとめを求めたときは、合意した構造、不変条件、判断理由、残る論点を簡潔にまとめる。必要な場合だけ最小限の型定義やデータ例を添え、提案と合意を区別する。

この skill の呼び出しだけでは実装やファイル変更を始めない。設計を理解するための調査は行い、実装や設計書の保存はユーザーの依頼範囲に従う。
